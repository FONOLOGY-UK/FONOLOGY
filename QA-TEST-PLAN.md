# Fonology — Master QA Test Plan

Covers all three interconnected systems and how they share data. Written from the actual
codebase (not a generic template) — every fact in Section 1–2 is verified against the source,
not assumed.

---

## 1. Project Overview

**Project name:** Fonology — a phone repair shop's storefront + back office, trading as
"Fonology" (Thornliebank, Glasgow).

**Components:**

| Component           | What it is                                                                                                                                                                                                                              |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Public Website**  | Storefront: product catalog (cases, chargers, audio, vaping, number plates, etc.), cart/checkout, repair booking (mail-in), sell-your-phone / trade-in submission, guest order/repair/sell tracking, customer accounts + Google sign-in |
| **Admin Panel**     | Owner-facing back office: orders, jobs (repair bench), inventory, promotions, labels, cash drawer, day-close, trade-ins + payouts, payments ledger, reports, staff roster, settings (incl. printers, delivery rates, opening hours)     |
| **POS ("Counter")** | In-store till used by employees: checkout/sale, jobs board, inventory, promotions, cash/float, walk-in trade-ins, "my day" sales total, barcode scanner, receipt/label printing                                                         |

**Tech stack:**

- **Frontend:** Next.js 15 (App Router, React 19), TanStack Query + Table, Zustand (cart/checkout
  state), React Hook Form + Zod, Tailwind CSS, GSAP/Lenis (motion), `apps/web`
- **Backend API:** Express 4 + Zod validation, `apps/api`, talks to Supabase with the service role
  key (`supabaseAdmin`) — the frontend **never** calls Supabase directly and never calls `fetch()`
  directly; everything routes through a `dataAdapter` → API
- **Database/Auth/Storage:** Supabase (Postgres + Supabase Auth + Storage), migration-based schema,
  pgTAP test suite in `supabase/tests`
- **Hardware bridge:** a separate local Windows service (`apps/print-agent`) polls a print-queue
  table and drives a USB ESC/POS receipt printer + a label printer — this is the only thing that
  can print
- **Hosting/env:** dev Supabase project is separate from production (`ohkvwqqtppvnxbvvdsfr` vs.
  `sbqqpuqoizyjzdcydqid`); the deploy target for `apps/web`/`apps/api` isn't this document's
  concern, but note `apps/web` builds with `output: 'standalone'`

**User roles** (real, from `permissions.config.ts`):

| Role                           | Where                                  | Can do                                                                                                                                                                                                                                      |
| ------------------------------ | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Guest**                      | Website                                | Browse, add to bag, guest checkout, submit a repair booking or sell request, track by reference+email                                                                                                                                       |
| **Registered Customer**        | Website                                | Everything a guest can, plus order history tied to account, Google sign-in                                                                                                                                                                  |
| **Employee ("Counter" staff)** | POS + limited storefront-admin overlap | `pos.operate`, `jobs.manage`, `inventory.manage`, `promotions.manage`, `cash.manage`, `tradein.manage`, `sales.today` (**today's total only, never history**) — explicitly locked out of Returns, Reports, Payments ledger, Staff, Settings |
| **Owner**                      | Admin Panel + POS                      | Everything Employee has, plus `costs.view`, `analytics.view`, `payments.view`, `reports.view`, `returns.manage`, `labels.manage`, `staff.manage`, `settings.manage`                                                                         |

Permissions are a **per-person set** (`session.permissions`), not just a role label — `can(role,
permission, permissions)` prefers the real set and only falls back to the role's default map.
UI hiding is not the enforcement boundary; every admin/POS API route re-checks server-side
(`requireStaff` + `requirePermission(...)`).

**Key integrations — and their REAL state, not assumed:**

| Integration                             | Real status                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Online card payment (Stripe) / Clearpay | **Mocked.** `apps/web/src/lib/payments/provider.ts` — `pay()` resolves "ok" after a fake 1.4s delay. No real charge is ever taken online today. Real Stripe integration is blocked on the client's Stripe account. **Do not file "payment declined doesn't work" bugs against this path — there is nothing behind it yet.**                                                            |
| POS in-store card payment               | **Manual, by design, client-signed-off** — not a stopgap. Staff key the amount into a physical card machine (POS 1 = currently Shift4, POS 2 = currently a Dojo PAX A920 — configurable label, not hardcoded), the customer pays on the machine, staff read the machine's own result and click "approved" or "cancelled" here. There is no SDK/reader integration and none is planned. |
| Promo codes                             | **One hardcoded demo code** (`FIXED10`, 10% off) — there is deliberately no promotion engine. Not a bug if other codes fail.                                                                                                                                                                                                                                                           |
| Transactional email                     | **Real** — Brevo API (password reset, sell-request quote/acceptance links). Degrades gracefully (route still succeeds) if the API key is unset; test both states if possible.                                                                                                                                                                                                          |
| Barcode scanner                         | Keyboard-wedge device (types into a focused input, not a real device API) — a dedicated test page exists at `/pos/scanner-test`.                                                                                                                                                                                                                                                       |
| Receipt/label printing                  | Real — via the local `print-agent` service and a real ESC/POS thermal printer + label printer. `codepage`/`codepageCandidates` handle £-sign vs. accented-character tradeoffs; cp852 support on the actual printer hardware is unverified.                                                                                                                                             |
| Auth                                    | Supabase Auth, `httpOnly` cookies (never readable from JS): access token 1hr, refresh token 30 days, separate staff-session cookie 30 days. `Secure` flag on in production, `SameSite=Lax`. Google OAuth for customers.                                                                                                                                                                |
| Money                                   | Integer **pence**, server-computed everywhere, **no VAT anywhere** (Fonology is not VAT-registered — this is a deliberate, hard business rule, not a gap)                                                                                                                                                                                                                              |

**Environments to test:** dev only for anything destructive/staff-facing (`ohkvwqqtppvnxbvvdsfr`).
Browsers: Chrome, Safari (iOS is a real customer platform for this shop), Firefox. Devices:
desktop admin/POS use, mobile-first storefront (the POS till itself typically runs on a fixed
in-store PC/tablet — confirm actual hardware with the client before assuming touch-only).

## 2. Core User Flows

| Flow                              | Component                | Roles                              | Notes                                                                                                                                                                        |
| --------------------------------- | ------------------------ | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browse/search/filter catalog      | Website                  | Guest, Customer                    | Category tabs, search box, out-of-stock and "in-store only" (e.g. vapes) states exist by design                                                                              |
| Product detail → add to bag       | Website                  | Guest, Customer                    | Delivery hint here must say "from £x" (postcode-derived real fee quoted only at checkout)                                                                                    |
| Bag → checkout                    | Website                  | Guest, Customer                    | Guest checkout supported; delivery speed (collect/standard/next-day) picked here; promo field exercises the one demo code; payment step is mocked                            |
| Customer account + Google sign-in | Website                  | Guest → Customer                   | `/login` (customer) is separate from `/staff-login`                                                                                                                          |
| Forgot password                   | Website                  | Customer, Staff                    | Always returns a generic "if that email exists..." message — must never confirm/deny an account exists                                                                       |
| Mail-in repair booking            | Website                  | Guest, Customer                    | Real price quoted server-side at booking time (not an estimate); real reference minted immediately                                                                           |
| Sell-your-phone submission        | Website                  | Guest, Customer                    | **No price at submission** — staff quotes after inspection; customer accepts via a one-time emailed token link (`/sell/accept`)                                              |
| Guest tracking                    | Website                  | Guest                              | `/track` — reference + email, works for orders, repair bookings, and sell requests                                                                                           |
| Staff sign-in                     | POS/Admin                | Employee, Owner                    | Owner → `/admin`, Employee → `/pos`                                                                                                                                          |
| Till sale                         | POS                      | Employee, Owner                    | Cash / POS1 / POS2 (manual card) / transfer, split payments must sum exactly to the total, below-cost sales require a reason but are never blocked                           |
| Jobs board (bench)                | POS + Admin              | Employee, Owner                    | Mail-in bookings and walk-in jobs both land here once converted/created; a job can be cancelled with a reason and a "device returned" flag                                   |
| Inventory management              | POS + Admin              | Employee, Owner                    | Stock consumption is atomic and channel-agnostic (till sale, online order, or admin adjustment all go through the same function)                                             |
| Trade-ins queue + payout          | Admin (+ walk-in at POS) | Employee (`tradein.manage`), Owner | Quote is always a human figure, never calculated; payout is money OUT, excluded from revenue; a paid-out payout can optionally restock the device as a new product           |
| Returns/refunds                   | Admin                    | **Owner only** (`returns.manage`)  | Employee accounts are explicitly gated out; refund amount is server-computed/integer pence; refund gets its own `REF-` reference distinct from the original sale's reference |
| Cash drawer / float               | POS + Admin              | Employee, Owner                    | Float counted at open, petty cash tracked separately from sales                                                                                                              |
| Day-close reconciliation          | Admin                    | Owner                              | Deferred DB constraint: sum of payment legs must equal the sale total at commit                                                                                              |
| Reports/analytics                 | Admin                    | **Owner only**                     | Employees see `sales.today` (today's total, never history) via POS "My day" instead                                                                                          |
| Printing                          | POS + Admin              | Employee, Owner                    | Till receipt, refund receipt (gated on `returns.manage`, not `pos.operate`), labels — all real hardware output via print-agent                                               |

## 9. Regression checklist — run after every deployment

These are the paths where a break is expensive (money, data integrity, or a customer-visible
promise) — re-run this short list every time, even for "small" changes elsewhere.

1. **Guest checkout completes** and produces a real order (WEB-006)
2. **Till sale with split payment** sums correctly and refuses if it doesn't (POS-005, EDG-015)
3. **Below-cost sale is never blocked**, only flagged (POS-008)
4. **Refund amount field replaces on type**, doesn't concatenate (ADM-012, EDG-006)
5. **Trade-in device names show real names, never UUIDs** — queue, detail, and payout label (ADM-005, ADM-006, ADM-009)
6. **Employee cannot reach Returns/Reports/Staff/Settings** by URL or direct API call (NEG-007, NEG-008)
7. **Forgot-password gives the same generic response** whether or not the email exists (NEG-011)
8. **Delivery hints agree** across PDP, bag drawer, and real checkout fee (XSYS-014)
9. **Refund reference is distinct from the sale reference**, especially on partial refunds (XSYS-007)
10. **Day-close totals reconcile exactly**, in pence (XSYS-009)
11. **Stock consumption is atomic and channel-agnostic** — a POS sale and an online order can't both take the last unit (EDG-010, XSYS-001/002)
12. **Guest tracking requires the matching email**, reference alone is never enough (NEG-010)
13. **Print-agent failure doesn't block or lose the underlying sale/refund/booking** (XSYS-012)

## 10. Must-test-before-launch blockers vs. nice-to-have

**Blockers (must pass before any production deploy):**

- All of Section 9 (Regression checklist)
- NEG-007, NEG-008, NEG-009 (role/API escalation — money and PII exposure risk)
- SEC-002 (brute-force lockout — **verify this exists at all**; if it doesn't, this is a launch blocker to build, not just test)
- SEC-010 (confirm no card data ever touches Fonology's systems)
- EDG-010, EDG-013, EDG-015 (concurrency/reliability around money and stock)
- XSYS-009, XSYS-012 (day-close integrity; print failure doesn't lose a transaction)
- NEG-013, NEG-014, NEG-015 (double-submit protection on every money-moving action)

**Known, deliberate gaps — not launch blockers, don't file as bugs:**

- Online Stripe/Clearpay payment is mocked (no real charge) — blocked on the client's Stripe account, tracked separately from this test plan
- No real promotion engine — `FIXED10` is the only code, by design
- POS card payment has no reader integration — manual entry + staff confirmation is the actual signed-off process, not a placeholder

**Nice-to-have (schedule after launch-critical coverage):**

- Section 8 (Non-functional) items NFR-001, NFR-003, NFR-005, NFR-009
- XSYS-013 (real-time vs. poll-based sync — cosmetic unless the interval is unreasonable)
